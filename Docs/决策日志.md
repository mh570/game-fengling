# 决策日志

**用途**：记录**每个重要决定的理由**，防止后来者（或未来的我）重复论证或推翻已定事项。
**规则**：每次做出影响方向的决策，追加一条。

---

## D-001 · 美术方向定为风格化

**日期**：2026-11-21
**决定**：走风格化（有限调色板、低对比、手绘感），不走写实。
**理由**：
- 目标参考视频就是风格化
- 单人 + 1 协作者做不了写实资产量
- 风格化对技术缺陷更宽容（低对比掩盖阴影/水面的瑕疵）
- 程序化生成在风格化下像"设计"，在写实下像"没做完"
**来源**：`Docs/analysis/05-风格化美术规范.md`

## D-002 · 像素感靠低分辨率渲染，不买像素资产

**日期**：2026-11-21
**决定**：渲染到 480×270 再点采样放大，而不是买 pixel-art 资产包。
**理由**：参考视频的阶梯边缘来自低分辨率渲染，任何低多边形资产经过这层都会呈现同样质感。成本几乎为零。
**替代方案（被否）**：买 Blockwood / Retro Pixel Forest（付费，且风格仍不完全一致）。

## D-003 · 资产只用免费/CC0

**日期**：2026-11-21
**决定**：预算为零，只用 CC0 或免费资源。
**现状**：Quaternius（CC0，需手动下）、Kenney（CC0，需手动下）、CC0Tree（已下载，但主要是道具）。
**阻塞**：itch.io / Kenney 无直链，需用户浏览器点击。

## D-004 · 地形改用 Unity Terrain

**日期**：2026-11-21
**决定**：放弃自写的 `CoastTerrain` 网格，改用 Unity 内置 Terrain。
**理由**：Unity Terrain 自带 LOD、草、树 instancing、splat 混合、碰撞——这些正是差距表里的"缺功能"。
**代价**：要给自建 SRP 写 terrain shader（目前地形是洋红）。
**来源**：`Docs/analysis/06-超大地图.md`

## D-005 · 岛用真实地形 1:1 复刻

**日期**：2026-11-21
**决定**：取 Skye 岛 Trotternish 海岸 2.6km 范围，用真实 DEM 高程。
**数据**：AWS Terrarium 瓦片，z=15，1025×1025，-50~478.6m，32% 海面。
**理由**：真实地形比程序化更有说服力，且免费可得。

## D-006 · 海水与参考浅水区分设计

**日期**：2026-11-21
**决定**：海/湖/河三种水体分开做；海分三段（近岸看底 / 中景波浪 / 远景化雾）。
**理由**：参考 01 是浅水湖，我们是海，不能照搬。
**沿用手法**：深度双色、岸线白边、离散高光。
**来源**：`Docs/video-analysis/01b-海水设计.md`

## D-007 · 自建 SRP 暂不迁移 URP

**日期**：2026-11-21
**决定**：先不决策，继续用自建管线把画面做出来。
**理由**：迁 URP 要 2-3 周且会丢掉月亮阴影（URP 只支持一个方向光阴影）。
**保留的观察**：Unity 官方 2026 路线倾向"模块化 URP + Render Graph"，长期看自建管线有维护风险。
**触发重议的条件**：如果自建管线连续阻碍视觉实现（比如 terrain shader 写不出来），重新评估。

## D-008 · 工作方式：小循环 + 文档即记忆

**日期**：2026-11-21
**决定**：
- 分析 1 个视频 → 实现 1 项 → 验证 → 提交 → 更新文档
- `Docs/总任务.md` 必须可"冷启动"（新会话读完就能接手）
- 每轮结束都是可接手状态
**理由**：上下文有限，一次做太多会丢失细节、分析变糙。

## D-009 · 白色亮线描边是风格核心

**日期**：2026-11-21
**决定**：把"边缘亮线后处理"提到优先级第一。
**理由**：01（岸线白边）和 02（路面/台阶白虚线）都有这个特征，是让画面有"手绘插画感"的关键，且实现成本低（深度/法线边缘检测）。
**来源**：`Docs/video-analysis/01-分析.md`、`02-分析.md`

## D-010 · 图2 是树冠子项目的主验收目标（不是整个游戏最终目标）

**日期**：2026-11-22
**决定**：图2（`02-trees/f_010.jpg` 右下树冠局部）作为**树冠 / hero shot 的主验收目标（T0）**；不是整个游戏画面的最终目标。
**范围限定**：
- 图2 负责“树冠 + 局部场景”的验收；
- 整体游戏仍以参考视频 BV1jEsC6jEAz 为目标（地形、水、GodRay、昼夜等都还在图2 之外）；
- 单帧容易过拟合，S7 额外做 3 个回归检查：3/4 视角、侧视、相机移动 1m / 旋转 30°（不闪、不跳、不穿帮）。
**理由**：图2 是视频压缩裁切，不能追 JPEG 噪点；树必须在游戏相机下成立，而不是只对这一张截图成立。
**执行落点**：`Docs/analysis/23-执行文档-图1到图2-分阶段与校验.md` 的 A0 / G7；目标裁切与 hash 锁定在 B0。
**后续**：D-011 把画幅扩展为 T1 1:1 + T2 16:9 双目标同权。
**来源**：用户 2026-11-22 判断 + 选项 A 确认。

## D-011 · 画幅双目标同权：T1 1:1 + T2 16:9

**日期**：2026-11-22
**决定**：图2 的验收拆成两个**同权**目标：
- **T1 1:1**：620×620，近景叶簇尺度；
- **T2 16:9**：800×450，游戏构图（树冠 + 树干 + 码头/水/草）。

**理由**：
- 游戏最终是 16:9，单用 1:1 会漏掉游戏构图；
- 1:1 又不能被 16:9 替代，否则叶簇尺度会被拉远、失真；
- 两者同权，才能同时约束“近看叶簇”和“远看构图”。

**T2 目标**：
- 裁切：f_010 `[1040,450,800,450]`
- 文件：`Docs/execution/fig1_to_fig2/B0/target_16x9.png`
- SHA256：`34F0F5516F37F54FB9495F615B7EB32C854CDE2A6B44ED81906C0AA7AD8AADD2`
- 剪影参考：`Docs/images/t3ss/fig1_fig2/t2_silhouette_guide.png`
- 剪影容差：**±15px**（用户手绘，近似轮廓，不做像素级 IoU）
- 读图：手绘轮廓 bbox 约 594×410（宽高比 **1.45**），主体是“一个连通的伞状冠 + 4–5 个叶团 + 底部树干缺口”，与执行文档的 3–5 叶团目标一致。

**影响**：
- S0.3 必须出两张 target camera：1:1 与 16:9；
- G1/A1 的构图指标拆成 T1/T2 两套；
- S2/G2 的剪影检查以 T2 手绘轮廓为参考带，允许 ±15px；
- G0 必须两张 target 都锁定、两台相机都可复现，才算通过。

**来源**：用户 2026-11-22 选择 C（双目标同权）+ 手绘 T2 剪影。
