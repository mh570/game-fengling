# 模块架构

游戏按"业务能力"切模块，模块之间是**包容关系**（环境里有水），但**依赖是单向的**。

---

## 1. 模块树

```
Game
└─ Environment（环境模块）
   ├─ Water（水）        ← 当前唯一在做的模块
   ├─ Terrain（地形）     ← 待建
   └─ Sky（天空）         ← 待建
└─ Actor（角色模块）
   └─ Player（玩家）      ← 极简，只负责把人带到水边
```

"包容"指的是**归属**：水属于环境，环境属于游戏。
但归属不等于依赖——水不知道环境存在，玩家不知道水是什么。

---

## 2. 依赖方向（这是全部的关键）

```
        ┌───────────────────────────┐
        │  Water.Abstractions       │  ← 只有接口，2 个文件
        │  IWaterSurface            │
        │  IWaterProvider           │
        └───────────┬───────────────┘
                    │ 被两边引用（依赖倒置）
        ┌───────────┴───────────┐
        │                       │
   Fengling.Water        Fengling.Player
   （实现 + 调参）         （只查询，不知道实现）
```

规则：

| 程序集 | 可以引用 | 不可以引用 |
|---|---|---|
| `Fengling.Water.Abstractions` | UnityEngine | 任何业务模块 |
| `Fengling.Water` | Abstractions、UnityEngine | **Player** |
| `Fengling.Player` | Abstractions、UnityEngine | **Water** |

三条硬约束：

1. **Water 不认识 Player** —— 水不知道有玩家这回事
2. **Player 不认识 Water** —— 玩家只知道"有个东西能告诉我水面多高"
3. **谁都不能绕过 Abstractions** —— 想加新模块（船、鱼漂），只准引用 Abstractions

**这些不是约定，是编译期强制的**：`Fengling.Player.asmdef` 的 references 里只有 `Fengling.Water.Abstractions`。写一句 `new GerstnerWaterSimulation()` 就编译不过。

---

## 3. 水模块内部（高内聚）

```
Water/
├─ Abstractions/          ← 对外插头（独立程序集）
│   ├─ IWaterSurface.cs       采样契约
│   └─ IWaterProvider.cs      查找标记
└─ Runtime/               ← 实现（独立程序集）
    ├─ WaterModule.cs          门面：场景里唯一入口
    ├─ WaterSettings.cs        参数
    ├─ IWaterSimulation.cs     内部发动机契约
    ├─ Simulations/
    │   ├─ FlatWaterSimulation.cs     对照组
    │   └─ GerstnerWaterSimulation.cs 第一版
    ├─ WaterFieldGizmo.cs      高度场线框（不用 shader 也能看）
    └─ WaterLabHUD.cs          运行时调参面板
```

**高内聚的检验标准**：把整个 `Water/` 目录删掉，工程里除了一个场景物体引用之外，不应该有任何编译错误。

### 为什么要有两套接口

| 接口 | 给谁 | 稳定性 |
|---|---|---|
| `IWaterSurface` | 外部（玩家、船、鱼漂） | **不能随便改**，改了所有调用方都要动 |
| `IWaterSimulation` | 模块内部（换算法） | 随便改，外部看不到 |

这是"高内聚"的真正含义：**变化被关在模块内部**。加一个 FFT 实现，只需要新增一个类 + 改 `WaterModule.Rebuild()` 的一行，外部零改动。

---

## 4. 玩家模块（极简）

```
Player/
├─ PlayerMotor.cs        WASD + 鼠标 + 跳跃 + 重力
└─ PlayerBuoyancy.cs     水里浮起来（IWaterSurface 的第一个消费者）
```

`PlayerBuoyancy` 有个细节值得注意——它**不引用 `WaterModule` 类型**，而是：

1. 启动时扫场景找 `IWaterProvider`
2. 拿 `p.Water`（类型是 `IWaterSurface`）

代价是一次启动查找，换来零编译期依赖。这是低耦合的具体成本，值得付。

---

## 5. 怎么加一个"船"模块

照抄玩家的模式，三步：

1. 新建 `Assets/Game/Actor/Boat/`，加 asmdef，references 只写 `Fengling.Water.Abstractions`
2. 写 `BoatFloatation.cs`，字段类型用 `IWaterSurface`
3. 启动时用同样的方式找 `IWaterProvider`

**不需要改水模块的任何一行代码。** 如果做不到这一点，说明水模块耦合没做干净。

## 7. 测试场景怎么搭

Unity 里手动搭一次（约 3 分钟）：

```
1. 新建空场景，命名 WaterLab
2. 空物体 "Water"
   ├─ 加 WaterModule          （参数默认已是 4 波 Gerstner）
   ├─ 加 WaterFieldGizmo      （Scene 视图里看波形）
   └─ 加 WaterLabHUD          （运行时面板）
3. 空物体 "Player"
   ├─ 加 CharacterController  （半径 0.4，高 1.8）
   ├─ 加 PlayerMotor          （cameraPivot 指向相机）
   └─ 加 PlayerBuoyancy
   └─ 位置放在 (0, 3, -20)
4. 主相机挂到 Player 下，LocalPosition (0, 1.6, 0)
5. 加一个 Plane 当地面（Y=0），尺寸 5×5
```

运行后按 `2` 切 Gerstner，`[` `]` 调振幅，`P` 定格，走到水边进水看浮力。

## 8. 验收：什么算"水模块做对了"

三条，缺一不可：

1. **删掉 Water 目录，只报一个错**（场景物体丢失组件），没有连锁编译错误
2. **新增一种水（FFT），只改 `WaterModule.Rebuild()` 一处**
3. **新增一个消费者（船），只引用 Abstractions，不改水**

三条都满足，这个模块才算真的"高内聚低耦合"，否则只是文件夹分层。
