# 外部方案分析（analysis）

**建立日期**：2026-11-21
**目的**：停止闭门造车。系统性地研究成熟项目的做法，对照我们的实现，形成可执行的迭代清单。

---

# 一、为什么要建这个文件夹

2026-11-21 之前的工作方式有问题：

- 遇到问题就在自己的代码里找原因、打补丁
- 没有对照"别人已经解决过的问题"
- 结果是**局部修补，整体观感依然差**

从今天起，每个模块都要先回答三个问题：

1. **别人怎么做**（成熟项目 / 官方方案 / 开源实现）
2. **我们差在哪**（具体到代码位置）
3. **怎么改**（可执行、可验证）

---

# 三、每个模块的分析模板

```markdown
## 现状（我们的实现）
- 文件、类、关键参数
- 已知问题（有证据）

## 外部方案
- 方案 A：谁做的、核心思路、成本、适用场景
- 方案 B：...
- 官方/引擎推荐做法
- 来源链接

## 差距
| 项 | 我们 | 别人 | 差距性质（缺功能 / 参数错 / 架构错） |

## 迭代计划
1. 具体改动（文件 + 函数）
2. 验证方式（探针 / 截图 / 断言）
3. 风险与回退
```

# 五、工作方式约定

1. **每个改动前先读对应分析文档**
2. **分析文档必须带来源链接**，不能凭印象
3. **对照表里写明"差距性质"**——参数错好改，架构错要重写，不能混为一谈
4. 迭代计划要能验证：探针 / 截图 / 断言，三者至少一个
