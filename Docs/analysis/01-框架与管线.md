# 01 · 框架与管线

**分析日期**：2026-11-21
**模块**：L0 引擎与管线框架
**我们的实现**：`Assets/Game/Rendering/FenglingPipeline.cs`（488 行）+ `FenglingPipelineAsset` + `FenglingShadows` + `FenglingClouds`

---

# 一、现状

| 项 | 我们的做法 |
|---|---|
| 管线类型 | **完全自建 SRP**（`RenderPipeline` 子类） |
| 渲染 API | `ScriptableRenderContext` + `CommandBuffer`（RenderGraph 之前的一代） |
| Pass 组织 | 一个 488 行的 `RenderCamera` 方法里顺序执行，无显式 Pass 结构 |
| 已迁移 | 包了一层 RenderGraph 的 `AddUnsafePass`（行为等价，但只是壳） |
| 废弃 API | `DrawRenderers` ×3、`DrawSkybox` ×1、`splitData` ×2 |

## 已知问题

1. **升级悬崖**：Unity 6.5 起 `ImportBackbuffer` 必须传 `RenderTargetInfo`、renderer list culling 移除，未迁移的自建 SRP 会**直接渲染失败**
2. **无 Pass 抽象**：加一个功能就是往 `RenderCamera` 里再塞一段，顺序靠注释维护
3. **后处理/半分辨率链路不通**：历史上 GodRay 半分辨率做不出来，就是这个原因

---

# 二、外部方案

## 方案 A：扩展 URP（官方推荐方向）

**谁在做**：Unity 官方。2026 路线明确说了方向。

> "the direction we are pushing with URP is to make this level of customization possible in a more modular way without needing to build a full pipeline from scratch. With the move to Render Graph and a more modular architecture, we expect that more advanced rendering techniques can be integrated directly into URP in a flexible way."

来源：[Render Pipelines strategy for 2026](https://discussions.unity.com/t/render-pipelines-strategy-for-2026/1710004/394)

**做法**：写 `ScriptableRendererFeature`，插进 URP 的 pass 队列。

| 优势 | 代价 |
|---|---|
| 阴影级联、透明排序、后处理、XR、多平台都是现成的 | 需要迁到 URP 的坐标/材质体系 |
| RenderGraph 迁移跟着官方走 | 自建的双光源阴影、天文天空要重写成 Feature |
| 未来版本升级不炸 | 已有 488 行管线代码大部分作废 |

## 方案 B：继续自建，但迁到标准 RenderGraph

**参考实现**：[Catlike Coding Custom SRP 7.x](https://catlikecoding.com/unity/custom-srp/7-0-0/) —— 从零构建到 RenderGraph 的完整教程，是目前最权威的自建 SRP 参考。

| 优势 | 代价 |
|---|---|
| 已验证成果（双光源阴影、天文）全部保留 | 要重写渲染循环为 RenderGraph pass |
| 完全控制 | 每个新特性都要自己接（透明、粒子、后处理、XR） |
| 没有 URP 的包袱 | Unity 升级仍可能踩坑，只是踩得比别人早 |

## 方案 C：URP + 自建 Feature（折中）

**做法**：底层用 URP，把我们的独有能力（真实日月、双光源阴影、自定义水体、体积云）做成 Feature。

| 优势 | 代价 |
|---|---|
| 复用 URP 的成熟基建 | 仍要重写我们的 shader 到 URP 光照模型 |
| 独有能力保留 | Feature 之间顺序和资源管理要重新设计 |

# 三、差距

| 项 | 我们 | 成熟项目 | 差距性质 |
|---|---|---|---|
| 渲染 API 世代 | RenderGraph 之前的写法 | RenderGraph | **架构错**（会随版本失效） |
| Pass 组织 | 单方法顺序执行 | 显式 Pass 队列（URP 四 block） | **架构错** |
| 透明/粒子路径 | 自己接，且历史上有坑 | 由管线提供 | **缺功能** |
| 后处理链 | 手写 Blit | 现成的 Volume/PostProcess 体系 | **缺功能** |
| 升级风险 | 高（6.5 会炸） | 跟随官方 | **架构错** |

---

# 四、核心判断

**我们面对的不是"bug 多"，而是"基建选型未经验证"。**

自建 SRP 适合：
- 有专门图形程序、愿意长期维护
- 需求与通用管线差异极大（比如体素、特殊坐标）

我们的需求（地表 RPG 环境 + 真实日月 + 水体 + 云）**URP 完全覆盖**，且有大量成熟实现可抄。

## 但——已经投入的事实

| 已实现且验证有效的 | 迁移成本 |
|---|---|
| 太阳 4 级级联 + 4096 atlas | 中（URP 有级联阴影，但要换） |
| 月亮独立 2048 阴影 | 高（URP 无第二方向光阴影） |
| 真实日月天文 | 低（纯计算，与管线无关） |
| 自定义水体 | 中（URP 有水面但不满足） |
| 体积云 | 低（与管线无关，只依赖深度） |

**月亮阴影是唯一"URP 做不到"的能力**（URP 只支持一个方向光阴影）。这是自建 SRP 的**唯一硬理由**。

# 五、迭代计划（待决策）

## 选项 1：继续自建，补 RenderGraph（保守）

1. 把 `RenderCamera` 拆成显式 Pass（参照 URP 四 block）
2. 逐个 pass 从 `AddUnsafePass` 转 `AddRasterRenderPass`
3. 迁 `RenderTargetInfo` / `CullShadowCasters`
4. 验证：探针偏差 < 5

**工期**：3-5 天。风险：中。收益：保住现有成果，但不解决"功能少、维护累"的根本问题。

## 选项 2：迁到 URP + 自定义 Feature（激进）

1. 保留天文/云/水体 shader 逻辑，重写到 URP 体系
2. 月亮阴影做成自定义 Feature（这是唯一无法用 URP 现成能力替代的）
3. 废弃 `FenglingPipeline`

**工期**：2-3 周。风险：高。收益：基建归零重来，长期最省心。

## 选项 3：先做视觉，后决定（拖延）

不建议——视觉问题很多继承自基建缺陷。

# 六、结论

**这是个需要你拍板的战略决策，不是技术细节。**

我的判断：

> 如果这个项目是**长期商业项目**（你说是 Steam 独立游戏），且**只有你一个人（+1 协作者）维护**，那么**选项 2（迁 URP）长期成本更低**。
>
> 但它的前期投入大，且会丢掉已调好的月亮阴影。

**建议先做一件事再决定**：花半天时间，用 URP 建一个最小场景，把我们现在的 Lake 地形/水体/云摆进去，看**同样的美术资源在 URP 下是什么观感**。这个对比结果会直接回答"是基建问题还是内容问题"。
